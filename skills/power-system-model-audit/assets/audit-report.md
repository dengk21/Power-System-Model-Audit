# Power System Model Audit 模型检查报告

本报告说明检查了哪些内容、发现什么问题，以及判断和修改的依据。同目录的`audit_brief.md`用于快速查看问题位置和处理方法。

## 输入与环境

记录实际运行入口、原始数学说明、参数、修改前后的代码和结果，并附文件校验值（SHA-256），便于确认对应版本。同时说明采用哪些物理或数学依据、这些依据是否已核对，以及各工况使用的求解器、求解状态和新增求解次数。

## 检查范围与映射

先说明本次是使用已有结果验算（replay）、进一步定位问题（diagnose），还是重新求解并保存结果（capture）。列出实际操作、次数、单次与总时间限制及耗时。进一步诊断与重新求解分别记录；已有记录缺失、文件已改变或执行失败时，说明缺少什么，不把它写成检查通过，也不自动增加求解。

使用collect时，直接引用execution.json和acceptance.json中的命令、时间、退出状态和文件版本，避免重复填写两套统计。`COLLECTED_NOT_REVIEWED`表示已记录运行、尚待审阅，应与数值检查通过及数学判断分开说明。失败和超时同样保留日志。

同时检查多个模型时，先列出全部入口、模型类型、求解器和项目程序版本，再逐项说明是否运行、是否有有效结果、检查了什么、还有什么未完成。失败的入口也列入表中。

待检查关系应从实际代码中逐项整理，包括目标函数、等式、不等式、变量取值、边界和模块间关系。没有匹配知识卡的约束也要保留；缺少某类关系时说明原因。对每条关系分开写明：是否实现、是否执行、检查了哪些设备和时段、结论是什么。清单未整理完整时不计算全模型覆盖率。知识卡小例子的实际测试与复用旧测试结果的次数另列，避免与当前模型的数值检查混淆。

## 数学模型复核与错误归因

逐项说明是原公式错误、代码错误、两者有同一错误，还是说明遗漏或定义尚不明确。结合单位、守恒关系、推导、手算例子或独立来源解释原因。公式和代码写法一致，也需要检查共同采用的物理定义是否正确。

## ERROR

无错误时写明：本次已检查内容中未发现确定错误。

每项给出编号、问题、严重程度、公式或代码位置、涉及设备和时段、判断依据及修改建议。数值部分列出实际值、按参考公式算出的值、差值、单位、允许误差和违规数量。错误来源字段保留`MATHEMATICAL_MODEL/IMPLEMENTATION/BOTH/NUMERICAL_EVIDENCE/CHECKER/EXECUTION`，正文解释它分别对应公式、实现、共同错误、数值依据、检查程序或执行问题。原文错误而代码正确时，只要求修改原文。

## WARNING

需要补充说明或确认条件时，列明具体缺少什么、会怎样影响判断，以及下一步应核对什么。说明遗漏用`DOCUMENTATION_GAP`，参考定义存在分歧用`REFERENCE_CONFLICT`。代码正确但文字漏写时，要求补充说明，而不是修改代码。没有待确认问题时写“无”。

## 数学模型补全与修正草案

直接写出可补入报告的文字或LaTeX，给出完整公式、符号、单位、集合、边界、插入位置和对应代码，并说明依据。先确认模型是否需要这一关系，例如纯有功DC模型不补无功平衡。发现代码错误时，先纠正关系，再整理说明。

区分原始表述、从代码整理的草稿、已按明确假设核对的写法和待确认修改。获准修改原文时，记录原式、新式及文件校验值；尚未获准的修改先保存在报告中供确认。

## 独立数值证据

保留数值检查程序的原始统计表，说明哪些设备和时段通过、哪些缺数据、哪些关系不适用，以及哪些错误尚未在当前结果中表现出来。

## 模型间一致性（适用时）

在输入、目标和求解状态可比时，检查等价写法是否得到一致结果，限制收紧或放宽后是否符合预期。出现差异时，继续回到各自公式和独立检查结果寻找原因。

## 程序是否错误排除或放行运行方案

分别寻找“物理条件允许、程序却拒绝”和“程序允许、但违反物理条件”的方案。给出完整变量值、输入条件、来源，以及两侧的数值检查结果。`LOCAL_RELATIONS`只表示已检查局部关系，应说明完整模型还有哪些条件未检查。没有找到差异时，直接说明本次尝试范围。

## 尚待解决的问题与重新运行方法

列出输入、运行命令、程序和公式版本、已使用的次数及时间，并说明尚未确认的问题会怎样影响结论。

同时说明哪些通用工具可以直接使用，哪些项目程序已经实现，哪些模型已经实际检查，新模型还需要准备什么。
